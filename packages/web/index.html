    03 · How it works

    Four checks, each one a no.

    1. 01

      Public offer book

      Merchants post fixed fields: price, delivery, expiry. No free text on chain. Locked, 0 keys.

    2. 02

      Committed policy

      The buyer commits a hash of the scoring weights once, one-way, before any quote exists.

    3. 03

      Quote snapshot

      The book snapshots every valid offer for the item. The agent can't choose the list.

    4. 04

      Checkout gate

      Pays the seller only if the chosen offer is the quote's winner. Anything else: NotWinner.

    And the bribe money itself?

    It can't change the winner, and NEAR sent to the agent account ends up with the buyer.

    05 · The fine print

    What this does not stop.

    1. If the agent simply never buys, nothing on chain records that. The design controls what a purchase pays, not whether one happens.
    2. The buyer's own full-access key is the root of trust: whoever holds it can redeploy the agent account and move its balance. donate and sweep only bind while that key is safe.
    3. One live offer per seller per item stops a single spam account, but a funded attacker with many accounts can still fill the 64-offer cap.
    4. NEP-141 token kickbacks are not forwarded; the demo uses native NEAR. Bribes paid to the operator off chain are out of scope.
    5. The "naive agent" is a scripted baseline, not an LLM. The merchants are sub-accounts we created, each with its own key.
    6. The deployed code hash equals the hash we published. A byte-reproducible build is not done yet.

    Not the first: Gebele et al. (DeFi '25) gate settlement on a best-scoring rule inside a TEE. Loyal Cart does it over a public offer book with a buyer-authored policy and no TEE. More in related work.
